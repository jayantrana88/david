# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

This is a **job / internship applier** (repurposed from the Intellectiq lead-gen daemon; `socialmine-daemon-master/` stays in the repo for reference). A single-process asyncio **daemon** finds small companies (employee count ≤ a per-task limit, default 50) in a category and location, checks that each plausibly has work for the candidate, and writes each one an application with the candidate's **resume attached**. The candidate is one `candidate_profile` row: a resume uploaded on the dashboard's Profile page, the user's career notes, and the fields the AI derives from them (name, headline, skills, target roles, job/internship, links), all editable. The code and tables still say "lead" and `websites` for a company, and `cold_emails` for an application. Everything is in one local SQLite file, `daemon/data/david.db` (`daemon/db/schema.sql`; the daemon and the dashboard share it; uploaded resumes are files in `daemon/data/resumes/`).

**Repo layout**: the Python daemon lives in `daemon/`, and every Python path below (`core/`, `stages/`, `config.py`, `db/`, `data/`, `logs/`, `tests/` ...) is relative to it. The dashboard is `web/` (the React app) with `web/server/` (its local server; the Worker serves the same app and API). The Cloudflare Worker sits at the repo root (`wrangler.jsonc`, `package.json`, `src/`, `web/`, `migrations/`, `test/`, `scripts/`) so the Deploy to Cloudflare button can clone this repo directly; its docs are `docs/cloudflare.md`.

`main.py` starts one **worker per stage** (`POOLS` in `main.py`). The stages never call each other: each polls its own "pending work" query, so a lead flows on by itself once the previous stage has written its row. The sourcing stage's work comes from the user, as rows in the `tasks` table.

| Stage | Queue (`stages/<stage>/store.py`) | Logic (`run.py`) | Writes |
|---|---|---|---|
| `profile` | `pending_profile`: the `candidate_profile` row while `parse_status='pending'` (set by the dashboard on upload / re-derive) | `derive_profile` (resume text via pypdf / python-docx in `extract.py`, then the AI) | `candidate_profile` (derived fields + `done`/`failed` + `parse_error`; applied only if `updated_at` is unchanged) |
| `sourcing` | `next_pending_task`: the oldest `tasks` row with `status='pending'`, one at a time | `linkedin/` (`run_linkedin(task, known, save_lead)`) | `websites` (incl. `employee_size`, `employee_max`, `industry`, `linkedin_url`, the task's `target_role` / `opportunity_type`); its `tasks` row (`running` → `completed`/`failed`, `leads_saved`, `error`) |
| `scrape` | `pending_websites`: no `website_scrapes` row, or one still `is_qualified IS NULL`; empty until the profile is ready | `run_site_scrape` (Jina + the AI judges fit, batched in `qualify.py`) | `website_scrapes` (`is_qualified` True/False/NULL, `summary`, `homepage_text`, `main_links`) + `websites.email` |
| `internal` | `pending_scrapes`: qualified scrapes with no `website_pages` row, or only the `content_json IS NULL` placeholder | `run_internal_pages` (Jina, up to 5 subpages) | `website_pages` (delete-then-insert in one transaction) + subpage emails into `websites.email` |
| `email` | `uncontacted_leads`; empty until the profile is ready and (with `EMAIL.attach_resume`) a resume exists | `write_emails` (`writer.py`: the AI writes, rule-checked, first drafts batched) | `cold_emails` (`draft` in dry run; `sending` → `sent`/`send_failed`/`rejected` (or left `sending` when the outcome is unknown), or `generation_failed`; `attachment_name`, `delivery`) |

The `tasks` table is the sourcing stage's **work queue, filled by the user**, not lead bookkeeping. For leads there is **no reaper and no attempt-counter columns/functions anywhere** (that approach — `scrape_attempts`/`qualify_attempts`, `record_*_failure` — was tried and abandoned; don't reintroduce it, and don't grow `tasks` into it). A lead is pending until its row exists; failures that need retrying are tracked in memory only (see the Worker below).

## Setup & Running

`requirements.txt` + pip; `requirements-dev.txt` adds pytest. Python 3.10+ (the venv runs 3.14).

```powershell
pip install -r daemon/requirements.txt -r daemon/requirements-dev.txt
# LinkedIn pages are fetched through the installed Google Chrome by default; without Chrome:
#   playwright install chromium   and set Settings.browser_channel=None
python daemon/main.py                   # every stage
python daemon/main.py --pools profile scrape   # only some (profile sourcing scrape internal email)
python -m pytest daemon                 # daemon/tests/: no network, no keys (fake AI / Jina, temporary databases)

# delivery channels (config.py -> EMAIL.delivery): sign in once, then try one through the real API
python daemon/mail_setup.py connect gmail      # or outlook: browser sign-in, saves data/mail_tokens/<provider>.json
python daemon/mail_setup.py test gmail --to me@example.com [--resume cv.pdf]   # really sends one sample

# manual harness (real APIs, in memory only: never the DB, never sends):
python daemon/test_email.py https://acme.com --resume my_cv.pdf [--notes "..."] [--role "Data Analyst"] [--type internship]
```

`tests/conftest.py` points `DB_PATH` at an empty temporary database before anything imports `config`. The tests cover the email rules, reply parsing, the Worker's outcomes, every queue query (seeded temporary DB), the config models, and a scrape and an email round against a fake AI (`tests/test_rounds.py`). Run them after every change.

No database setup step: `db/schema.sql` is idempotent and applied whenever the daemon (`core/sqlite.py::connect`) or the dashboard (`web/server/db.ts`) opens the file (`DB_PATH` overrides the location). `CREATE TABLE IF NOT EXISTS` never changes an existing table, so a **column added or removed later must also go into `ADDED_COLUMNS` / `DROPPED_COLUMNS` in `core/sqlite.py`**, which `upgrade()` applies (checking each column, so it is safe on every open and on a fresh file). `*.sql` is git-ignored except `db/schema.sql`.

There is no `APP_MODE`: the API keys, the AI model and the email settings are saved on the dashboard's Settings page, in the database (`app_secrets`: `ai_api_key`, `jina_api_key`, `serper_api_key`, `telegram_bot_token` + `telegram_chat_id`, `gmail_client_id` + `gmail_client_secret`, `outlook_client_id` + `outlook_client_secret`; `app_settings`: `ai_model`, `cloudflare_account_id`, `email_*`), and `config.py` loads them once at import into `config.credentials` (a frozen dataclass). The only environment variable is the optional `DB_PATH`. Gmail and Outlook also need the refresh token `mail_setup.py connect` saves in `data/mail_tokens/<provider>.json`. A stage whose client can't be built (missing key → `RuntimeError` in its `make_worker`, or `config.AI_PROBLEM` for the AI roles) is not started; the others run. The keys are stored as plain text: the dashboard's optional password (`dashboard_lock` table, `dashboard/src/lib/lock.ts`, enforced by `dashboard/src/proxy.ts`) is the only protection, and the daemon never reads it.

## Architecture

- **Layout**: `core/` (shared plumbing, no business logic) ← `apis/` (one module per outside service) ← `prompts/` ← `stages/<stage>/` ← `main.py`. `config.py` is the settings file at the root.
  - `core/`: `worker.py` (Worker loop, `sleep_or_stop`, `gather_outcomes`), `errors.py` (`LeadFailed`, `LeadSkipped`), `db.py` (async `Db`/`Tx`), `sqlite.py` (sync connection, schema + `upgrade`, encode/decode, `insert_sql`/`set_clause`/`utc_now`), `llm.py` (`LLMClient`, `LLMUnavailable`/`LLMAuthError`/`LLMQuotaExhausted`, `ask_in_batches`), `limits.py`, `log.py`, `retry.py`, `http.py` (`HttpClient`, `browser_headers`, `normalize_url`), `clients.py` (getters), `config_models.py`, `app_settings.py`.
  - `apis/`: `jina.py`, `jina_parsing.py` (+ `link_selection.py`), `serper.py`, `telegram.py`, `gmail.py`, `outlook.py` (+ `mail.py`: `Attachment`, the send statuses, `build_message`, the OAuth token file + refresher, `OAuthMailer`), `browser.py` (the only place that imports `playwright`), `site_check.py`.
  - `prompts/`: `templates.py` (every prompt), `schemas.py` (each reply's JSON schema), `parsing.py` (lenient readers); import from the `prompts` package.
- **Per-stage files** (the same in every stage): `models.py` (dataclasses), `store.py` (**all** of the stage's SQL: its queue query and its writes), `run.py` (pure async logic, dataclass in and dataclass out, **never the DB**), `worker.py` (`make_worker(db)`: store → run → store). Extra modules where a stage needs them: `profile/extract.py`, `scrape/qualify.py`, `email/writer.py` + `recipients.py`, `sourcing/linkedin/`. **Import rule**: a stage imports `core/`, `apis/`, `prompts/` and, from other stages, only the candidate (`stages.profile.models`, `stages.profile.store.ProfileCache`); never another stage's worker, store or run.
- **Clients** come from `core.clients`: `get_llm("qualify" | "email" | "profile")`, `get_jina()`, `get_serper()`, `get_telegram()`, `get_gmail()`, `get_outlook()`, `get_mailer(delivery)` (the one for `EMAIL.delivery`), `get_site_checker()`, `get_http()`, `get_browser()`, `await get_db()`, lazy `lru_cache` singletons; `aclose_all()` on shutdown. `make_worker` builds the clients its stage needs up front, so a missing key raises `RuntimeError` there.
- **Worker loop** (`core/worker.py`, one generic `Worker`): `bind_pool` once, then load the queue into a buffer, drop items already handled (`_done`) or backing off (`_retry_at`), run a batch, record each item's outcome, reload when the buffer is empty, `sleep_or_stop(idle_sleep)` when idle. Items need `.id` and `.label`. A stage gives either `run(db, item)` (run for each item side by side) or `run_batch(db, items) -> list[outcome]` (None = success, else the exception; `gather_outcomes` helps). Outcomes: success → done; `LeadSkipped` → done, not counted; `LeadFailed` / any exception → **in memory only** `_retry_at[item.id] = now + failure_backoff` (1 h); `LeadFailed(permanent=True)` → done; `LLMUnavailable` → the stage holds `exc.hold_secs`, the item isn't counted (`LLMAuthError`: 15 min; `LLMQuotaExhausted`: until the earliest reset); `max_consecutive_failures` in a row → the stage holds `cooldown`. An optional `gate()` returning a reason holds the stage (the email stage's `max_sends_per_day`).
- **AI batching is explicit, per round**: the scrape and email workers use `run_batch`, so their logic sees the whole round. `core.llm.ask_in_batches(items, size, ask_batch, ask_one, what)` sends chunks of `size` in one call, asks every item a chunk leaves out alone (never guessed), with `attempts=1` after a chunk call that failed outright; an `LLMUnavailable` from a chunk call is each of its items' answer. It never raises (except on cancellation): every answer, or exception, comes back in order. `scrape/qualify.py::qualify_many` (size `AI.qualify_batch`) and `email/writer.py::write_many` (first drafts, size `AI.email_batch`) use it. A rewrite (a draft that failed `check_rules`) always goes out alone; only the first attempt is batched. `qualify_batch=1` / `email_batch=1` turns batching off. Each prompt in `prompts/templates.py` has a JSON schema in `prompts/schemas.py` (`QUALIFICATION`, `QUALIFICATION_BATCH`, `COLD_EMAIL`, `COLD_EMAIL_BATCH`, `CANDIDATE_PROFILE`) passed as `chat(prompt, response_format=...)`, and a lenient parser in `prompts/parsing.py`. A new prompt gets its schema and parser alongside it.
- **Scrape errors are data, not exceptions** (`stages/scrape/run.py`): a website's `website_url` is always present (sourcing guarantees it) and `run_site_scrape(jobs, profile, saved_reads)` never raises for a Jina or AI failure; every lead gets exactly one result, which becomes a row:

  | Jina | AI | `website_scrapes.is_qualified` |
  |---|---|---|
  | fails | — | `False`: terminal, this lead is never retried |
  | succeeds | answers | `True`/`False` |
  | succeeds | fails (any reason, incl. `LLMUnavailable`, or no clear true/false) | `NULL`: offered again by `pending_websites` |

  A queue item (`ScrapeJob`) with a `scrape_id` is a lead whose row is still NULL: Jina isn't re-fetched; the worker loads `store.saved_read` (`homepage_text`, or the old `raw_json` for rows saved before that column existed) and only the AI is asked again; the worker then `update_qualification`s the row, or reports `LeadFailed` (still no verdict, 1 h backoff). An `LLMUnavailable` rides on the result as `llm_error`: the worker saves the row first, then reports the error so the stage holds. Keep new failure modes in this stage shaped the same way: return a value that becomes a row; don't invent an attempt-counting mechanism.
- **Internal follows the same rule**: `run_internal_pages` never raises. No internal links → one `"Homepage only"` page. Links exist but every read fails → one placeholder `Page` with `content_json=None` (`PagesResult.fetch_failed=True`); `pending_scrapes` offers the lead again, and `persist_pages` deletes the lead's existing `website_pages` rows before inserting, so a retry replaces the placeholder.
- **The fit check is mandatory**: there is no switch to turn it off (the old `AI.qualification_enabled` / `ai_qualification_enabled` setting was removed; the column is in `DROPPED_COLUMNS`). The scrape stage always asks the AI and always needs the profile ready and the qualify client.
- **Adding a stage**: `stages/<name>/` with `models.py`, `store.py`, `run.py`, `worker.py` (`make_worker(db)`), and an entry in `POOLS` in `main.py` (which also names its log file).
- **Adding a lead source**: a package under `stages/sourcing/` exposing `async def run_<name>(task, known, save_lead) -> SourcingRun` that hands every lead (`LeadRecord`) to the injected `save_lead` (returns `SAVED`/`DUPLICATE`/`ERROR`; compare with `==`) and skips URLs in `known` (`core.http.normalize_url`); check the website with `get_site_checker().check(...)` before saving (dead sites are skipped, not added to `known`). Then its name in `SOURCES` and its call in `run_source` (`stages/sourcing/worker.py`), its client getters in `make_worker`, and the name in the `tasks.source` CHECK (`db/schema.sql`).
- **LinkedIn source** (`stages/sourcing/linkedin/`, the user's main focus): one `LinkedIn` object built from mixins — `search.py` (async `iter_companies` over Serper result pages, only as far as needed), `pages.py` (async `fetch_company` + `parse_company_page`, block handling; pages come through `get_browser()`, a real Chrome, because plain httpx gets 999 after a page or two: `Settings.transport="http"` switches back. One browser + context per run, so LinkedIn's guest cookies carry across pages; `run()` closes it in `finally`, and a browser that can't start is a `RunAborted`, not a block), `filters.py` (`check_location`, `normalize_website`, async `dns_resolves` / `evaluate`) — plus `settings.py`, `models.py` (`RunState`, `RunAborted`), `constants.py` and the offline gazetteer `geo.py`. `service.run_linkedin(task, known, save_lead)` is the entry. Saves exactly `candidates` leads per search unless the results run out. **Company size**: `Settings.max_employees` (default 50) is overridden per task; LinkedIn's size band must END at or below it (`employee_upper_bound`), unknown sizes are rejected, and `numberOfEmployees` from JSON-LD is the fallback when the About list has no "Company size".
- **Sourcing tasks** (`stages/sourcing/worker.py::run_task`): `store.claim_task` (a conditional `pending` → `running` update returning the fresh row; `None` = the user changed it, left alone) → `run_source` (loads `known_urls`, runs the source; `on_saved` bumps `tasks.leads_saved` after every saved lead, a progress counter only, never used to resume) → `store.finish_task` `completed` (a shortfall noted in `error`), or `failed` + `error` (a `ValueError` such as an unrecognised location, `SourcingRun.aborted`, `SourcingRun.failed`, or any exception), then `LeadFailed(permanent=True)` so the Worker logs it. No auto-retry: the user re-queues by setting `status='pending'`. `main.py` calls `reset_interrupted_tasks` once at start (`running` → `pending`; the task reruns in full and dedupe skips what it already saved). The Worker's item id is `"<id>@<updated_at>"`, and a DB trigger bumps `updated_at` on every update, so a re-queued task isn't filtered out by the in-memory `_done` set; `store` never sets `updated_at` itself.
- **Candidate profile, fit check and application**: `stages/profile/` derives the profile (`extract.py` turns a PDF/DOCX into text; `run.derive_profile` asks the AI with `profile_prompt` / `CANDIDATE_PROFILE`; a bad file or unusable reply becomes `parse_status='failed'` + `parse_error`, never an exception). `CandidateProfile` (`stages/profile/models.py`) is what the other stages read: `brief()` feeds every prompt, `seeking(task_role, task_type)` is the role asked about (a lead's `websites.target_role` / `opportunity_type`, set by its task, wins over the profile's), `links()` are the only links an email may carry. The scrape and email stages reload it through `stages.profile.store.ProfileCache` on every queue load (edits apply without a restart) and return an empty queue until it is `ready`. The fit check is `qualification_prompt(candidate, seeking, text)`; the batched form takes one candidate and `(seeking, text)` per company. The application is `cold_email_prompt(candidate, lead, research, links, feedback, instructions)` (`instructions` = `EMAIL.instructions`, the user's rules: they override the prompt's flow and style, never what `check_rules` enforces); `writer.compose` wraps it in "Hi <company> team," and `signature(profile)` (name, phone, links). `writer.check_rules` enforces: no dashes, no lists, 2 to 3 short paragraphs of 70 to 140 words, only the candidate's own links, and a mention of the attached resume. The email worker reads the resume file once per `resume_sha256` (`ResumeCache`); `apis.mail.Attachment(filename, content)` (attached by the mail providers; only its name appears in the Telegram message).
- **Email safety**: `config.EMAIL.mode` is `"dry_run"` (default; each application is saved as a `draft` row for review on the dashboard's Cold emails page and nothing is sent; the lead isn't drafted again since it now has a row; going to `send` deletes the drafts first (`store.clear_drafts`, once, in the email worker's loader) so those leads get a real application) or `"send"`. The send path in `stages/email/worker.py::deliver` must keep its order: `store.create_sending` (records `delivery`) → `mailer.send` → `store.mark_email`. A `send` returns `sent` / `send_failed` / `rejected` / `uncertain` (`apis/mail.py`); `uncertain` (a mail provider's answer was lost after the request went out) skips `mark_email`, so the row stays `sending`, the queue excludes it, and the lead is never emailed twice; `rejected` (the provider refused the address) is permanent. `NoApprovedDraft` (the AI answered, no draft passed the rules) writes a `generation_failed` row in send mode; an AI *error* is a retryable `LeadFailed` and records nothing. `cold_emails.status` is itself what `uncontacted_leads` reads (`draft`/`sending`/`sent`/`rejected`/`generation_failed` all exclude the lead, only `send_failed` is re-offered); every write replaces the row the lead already has (`_replace_email_row`), so a lead keeps exactly one `cold_emails` row. `uncontacted_leads` cuts each page's text in SQL to `writer.MAX_CONTEXT_CHARS` (the writer reads no more than that), so a queue load stays small.
- **Email delivery** (`EMAIL.delivery`, dashboard column `email_delivery`; every channel has the same `send(to, subject, text, attachments, *, from_name)`, the `apis.mail.Mailer` protocol):
  - `telegram` (`apis/telegram.py`, default): nothing is emailed to the company; each application is posted to the chat `TELEGRAM_CHAT_ID` through the bot `TELEGRAM_BOT_TOKEN` as one HTML message (address and subject as `<code>`, body as `<pre>`) with an inline keyboard of `copy_text` buttons: To, Subject, and the body in pieces of at most 256 chars (`chunk_text`; they paste back together). Over 4096 chars it falls back to plain split parts with the buttons on the last. A read timeout is `send_failed` (a second post to the user's chat is harmless).
  - `gmail` (`apis/gmail.py`, Gmail API, raw MIME through the upload endpoint) and `outlook` (`apis/outlook.py`, Microsoft Graph `sendMail`): `OAuthMailer` refreshes the access token from the stored refresh token (`OAuthToken`, outside the limiter; Microsoft's rotated refresh token is saved back), retries only what can't have gone through (connect failure, 401 once, 429 / 5xx), and a timeout after sending is `uncertain`.
- **Rate limiting** (`core/limits.py`): one limiter per outside API for the whole daemon, from `config.RATE_LIMITS` (`llm`, `jina`, `serper`, `linkedin`, `telegram`, `gmail`, `outlook`: concurrency + rpm), built at first use and shared by every stage that calls the API (all three AI roles share `llm`, since they are one Workers AI account; scrape and internal share `jina`). Clients wrap each outbound call in `async with limit("<api>"):`. Don't add `sleep`-based pacing for APIs; the LinkedIn source's random `li_delay_range` jitter is the one deliberate exception (anti-bot).
- **Retries**: `core.retry.with_retry(call, retry_on=..., attempts, base_delay, max_delay, label)` (jittered backoff, honours `Retry-After`); put `async with limit(...)` *inside* the retried call. DB: `core.db.Db` runs `fetch_all` / `fetch_one` / `execute` (SQL + params) on its own single thread and retries only "database is locked"; writes that replace rows go through `db.transaction(fn)`. JSON columns (`core/sqlite.JSON_COLUMNS`) and booleans (`BOOL_COLUMNS`) are converted at the edge; timestamps are ISO-8601 UTC text (`utc_now()`).
- **AI**: three roles, `AI.qualify` (scrape), `AI.email` (email) and `AI.profile` (profile), all currently `CLOUDFLARE_GEMMA` (`openai/@cf/google/gemma-4-26b-a4b-it` through Workers AI's OpenAI-compatible endpoint, `api_base` built from `CLOUDFLARE_ACCOUNT_ID`, thinking turned off). `core.llm.LLMClient` (LiteLLM `acompletion`) is built per role at the first `get_llm(role)` call. A profile's `models` is an ordered fallback chain: a quota-exhausted 429 (a per-day `TPD`/`RPD` / `free-models-per-day` message, or a wait > `quota_switch_after`) rests that model until the reset the provider gave (in memory, `LLMClient._resting`) and the next model is asked at once; a withdrawn model (404 / decommissioned) rests 15 min; every model resting → `LLMQuotaExhausted(hold_secs=earliest reset)`; an auth error → `LLMAuthError`, no fallback. A per-minute 429 is retried on the same model by `with_retry`. Each profile's `structured_output` (`json_schema` default / `json_object` / `off`) steps down for a provider that rejects schemas. `extra_params={"mock_response": '{"qualified": true}'}` answers offline. Nothing else may import `litellm`. Set a stage's log level to DEBUG to see per-call token usage.
- **Config** (`config.py`): plain Python, validated on import by the frozen, strict pydantic models in `core/config_models.py` (`LoggingConfig`, `ApiLimit`, `LLMProfile`, `AIConfig`, `EmailConfig`; an unknown field or bad value raises `ConfigError` naming the field; `.updated(**fields)` returns a re-validated copy). Holds `Credentials`, `RATE_LIMITS`, `LOGGING`, `AI` (`qualify_batch` 1–30, `email_batch` 1–10) and `EMAIL` (`enabled`, `mode`, `delivery` (`telegram` / `gmail` / `outlook`), `max_sends_per_day`, `attach_resume`: attach the resume to every email and hold the stage until there is one, `instructions`: the user's own writing rules from the dashboard, column `email_instructions`).
- **Dashboard settings** (`core/app_settings.py`): `config.py` reads the single-row `app_settings` + `app_secrets` tables once, synchronously, at import (an empty database = defaults), applied over `credentials` (the keys), `AI` (`ai_model` for every role with the same AI key, else Workers AI's Gemma with `cloudflare_account_id`; batch sizes and the rest are config.py only) and `EMAIL` (non-NULL columns only, re-validated). `EMAIL.mode` defaults to `dry_run`; the user switches it to `send` on the dashboard. `main.py` writes `applied_version/applied_at/apply_error` back (also when `config.py` fails to import) so the dashboard (`dashboard/`, Next.js) can show what the daemon runs. `python main.py` is a small supervisor that runs the daemon as a child process (`DAVID_CHILD=1`); the child polls `app_settings.version` every 5 s (`_watch_settings`) and, when the dashboard saves a change, drains gracefully and exits with code 75, which the supervisor answers by launching a fresh child (config is read at import, so a new process is the only way to apply it). Any other exit code ends the supervisor, so a setting that makes `config.py` fail leaves the daemon stopped, with the reason in `apply_error`. Rate limits and logging are not DB-backed.
- **Logging** (`core/log.py`): `setup_logging(pools)` once (main.py passes `POOLS`; harnesses pass nothing). Daemon loops log via `logging.getLogger(__name__)` → `logs/main/main.log` + console. Stage logic and clients log via `slog(msg, level=..., exc_info=...)`, which routes to `logs/<pool>/<pool>.log` (file-only) inside a worker (a contextvar bound by the Worker) and to the `main` logger outside one. Levels: `config.LOGGING` (`levels` keyed by `"main"` or a pool name), the `LOG_LEVEL` env var overrides. Don't `print()` progress.
- **Dedupe**: in-memory only — `run_source` loads `known` (`stages/sourcing/store.py::known_urls`, normalized with `core.http.normalize_url`) once per task and the source skips URLs already in it. `store.insert_website` still maps a unique violation to `DUPLICATE` if the DB happens to have its own unique index, but nothing here creates one.
- **Dashboard** (one app, two hosts): `web/` is a Vite + React single-page app (Tailwind + shadcn components, `web/src/pages/*`, `web/src/lib/api.ts` for fetching and `web/src/lib/actions.ts` for what a button posts, `web/src/lib/types.ts` for the row shapes). It talks only to a JSON API, `src/api/`: `data.ts` (reads), `actions.ts` / `profile.ts` / `lock.ts` (writes: each answers an `ActionResult` `{ ok, message, fieldErrors? }`), `auth.ts` (the optional password and session cookie), `router.ts` (routes + the password gate + the CSRF origin check). Those handlers know the machine only through a `Host` (`src/api/http.ts`): the database (`ApiDb`), how to wake a stage or forget an item's retry mark (the Worker's `backoff` / `stage_state`; no-ops locally, the daemon polls), where the resume lives, how a password is hashed, and the host's own routes (settings; on the Worker also logs, "Run now" and the Gmail / Outlook sign-in). **Never import `src/core.ts`, the stages or any Worker binding (`Env`, D1 types) from `src/api/*.ts` outside `worker/`**: the local server runs them under Node (`tsc -p web/server` checks that). Worker host: `src/api/worker/` over D1. Local host: `web/server/` (`host.ts`, `settings.ts` over `app_settings` / `app_secrets` exactly as the daemon reads them, `db.ts` over `node:sqlite` with the schema applied on open, `server.ts` serving `web/dist` + the API on `127.0.0.1:3000`; `npm run dashboard`). The session's `worker` flag and Settings' `host` field switch the Worker-only parts of the UI (Logs, Stages / Run now, Stop, mailboxes, sourcing settings) on and off. Changing a page: edit `web/src/pages` and, if it needs data, `src/api/`; both hosts get it. `test/api.test.ts` (Worker host) and `test/local.test.ts` (local host) check the API; `npm run typecheck` checks the worker, `web/` and `web/server/`.
- **Cloudflare port** (the repo root: `wrangler.jsonc`, `package.json`, `src/`, `migrations/`, `test/`, `scripts/`, TypeScript, deployed by the README's Deploy to Cloudflare button, which clones this repo (`jayantrana88/david`) and finds `wrangler.jsonc` at its root. The Worker applies `migrations/` to D1 itself (`src/migrations.ts`, bundled via the `rules` in `wrangler.jsonc`; a new migration file is one more import there), so any deploy command works; see `docs/cloudflare.md`): the same pipeline as one Worker on the free plan (10 ms CPU and 50 outside requests per invocation, so a cron tick every minute runs ONE stage a small step: `src/runner.ts`). Same tables in D1 (`migrations/0001_init.sql`; the root `.gitignore` whitelists it), plus Worker-only state the daemon keeps in memory: `tasks.cursor` (a search's progress across ticks), `stage_state` (hold / idle / lease / fail streak), `backoff` (an item's retry time, never a counter), `mail_tokens`, `geo_cache`, `logs`, `resume_files` (the resume as base64). It is a port, not a wrapper: **a change to a prompt, a rule, a queue query or a stage's outcome here must be made in the Worker's `src/` too** (`src/prompts.ts`, `src/stages/writer.ts`, `src/stages/*.ts`, `src/jina.ts`, `src/sourcing/`), and `test/` checks parity (`npm test` at the repo root). Differences: Workers AI binding or any OpenAI-compatible endpoint instead of LiteLLM; `AI.toMarkdown` instead of pypdf / python-docx; Browser Rendering (or fetch) instead of Playwright; Open-Meteo geocoding (cached) instead of geonamescache (countries / subdivisions are generated into `src/sourcing/geo-data.ts` by `scripts/make_geo_data.py`); the same React dashboard as the local one (the **Dashboard** bullet), served as static assets so the UI costs no Worker CPU: `wrangler.jsonc` `assets` with `run_worker_first: ["/api/*", "/oauth/*"]`, and `build.command` builds `web/dist` before every deploy / `wrangler dev`. Its password is optional (open until one is set on its Settings page: a salted hash in the `dashboard_lock` table, `migrations/0002_dashboard_lock.sql`; the `DASHBOARD_PASSWORD` secret, if set, wins; `src/api/auth.ts`), and the deploy never asks for it (don't list it in `package.json` `cloudflare.bindings` or a `.dev.vars.example`: the button prompts for both); Gmail / Outlook connected by a web OAuth flow.
- **Jina**: `JinaClient.read` returns Jina's JSON or `None` (logged). `apis.jina_parsing.parse_jina_response` returns an `emails` key the scrape stage writes to `websites.email` (which `uncontacted_leads` depends on) — don't drop it.
